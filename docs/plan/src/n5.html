What breaks it

threat model, and one control that's theatre

Being single-user deletes most of a normal threat model: no multi-tenancy, no account takeover, no authentication surface, no session management. What's left is smaller but sharper, and one mitigation that almost every desktop finance app ships is largely theatre against the adversary you actually have. I'd rather say that plainly than let it sit in a security section looking like protection.

DPAPI is not protecting you, and I'd rather you knew

CryptProtectData binds a secret to your user account — which means any process running as you can call CryptUnprotectData and get the plaintext. That is precisely, literally, what the current infostealer families do; it is their main loop. Chrome's App-Bound Encryption tried to fix this exact class of problem with an elevation-service identity check and was bypassed in about 45 days, then broken structurally.

What genuinely raises the bar: CNG with VBS / Credential-Guard-class key isolation, or the TPM platform provider, plus a user passphrase (Argon2id) so the ciphertext isn't silently machine-recoverable. SQLCipher, EFS and BitLocker protect you against a stolen laptop — a real threat, but not this one.

And now the part I'd insist on saying, because it's narrower than it looks. VBS isolation stops the key being stolen. It does not stop it being used. A CNG persisted key is protected by a container ACL naming the creating user, so malware running as you can simply ask the key to decrypt and read plaintext back out of the oracle. The real gain is defeating offline and passive file theft, and forcing the attacker to stay resident on the machine — which only helps if something is looking for residency. So: plan the detection, or don't claim the benefit. Half of security engineering is refusing to bank a control you haven't finished building.

The exploit chain adversarial review found, which I'd not have caught unprompted

The natural-language screener compiles model output into SQL and runs it against DuckDB. Chain that to untrusted content and you have injected filing text → model-authored query → database engine. DuckDB by default can INSTALL and LOAD extensions, read http:// URLs, and COPY TO a UNC path. That's arbitrary read and exfiltration, launched from a hostile footnote, through a feature that looks like a safety property because "the model never produces the rows, it only produces the query".

The fix is cheap and has to be in from day one, because retrofitting it means auditing every query path: generated SQL runs on a separate read-only connection with extension loading, external filesystem and network access all disabled, against an allow-list of queryable views rather than raw tables, with a statement timeout and a parsed-AST check that rejects anything which isn't a single SELECT. Better still, compile to a restricted query AST rather than to SQL text at all — then the dangerous constructs have no way to be expressed.

The LLM boundary

This is the largest genuinely new attack surface in the design, and it isn't hypothetical. Filings, RNS announcements, news and PDFs are attacker-controlled text that you have asked the machine to read carefully and act on. A hostile 8-K footnote is indirect prompt injection with a direct payoff.

ControlImplementation
AI can read, cannot actArchitectural, not a prompt rule. The analysis service holds no credentials, no filesystem write, and no handle to the broker bridge. This matters more than credential scoping precisely because the bridge sits next to a trading-capable API.
Untrusted-content firewallEvery ingested document is parsed, stripped of hidden and zero-width characters, and provenance-tagged before it can reach a context window.
Sanitised renderAllow-listed markdown → HTML inside a restrictive CSP. No remote images, no script, no iframes.
Egress allow-listOutbound hosts enumerated and enforced, with a live console showing every host, byte count and quota burn. A domain allow-list is not a confidentiality control for hosts that log requests — it's a blast-radius control. Different thing.
Purpose-tagged data flowEvery outbound request carries a purpose tag (Display / NonDisplay / LlmPrompt / Export) checked against the licence class of the data it carries, with a build-breaking test.
Query sandboxAs above. Non-negotiable, in from the first screener commit.
No third-party plugins or MCPA non-goal precisely because it would puncture this boundary. Every extension point is a hole in the only thing keeping untrusted text safe.

Things I'd refuse to ship

  • DPAPI alone for secrets, presented as protection. It isn't, against the realistic adversary, and describing it as protection is worse than having nothing because it stops you building the real control.
  • A "not financial advice" disclaimer standing in for a design control. Disclaimers constrain nobody's behaviour. Architecture does.
  • Trusting the model to obey a prompt-level rule that matters. If it matters, it's enforced in code. A prompt is a preference, not a boundary.
  • Blanket telemetry with an opt-out. Local-only by default, explicit opt-in to send.
  • Claiming zero data retention that the account tier does not actually provide.
  • Storing the pack signing key anywhere an automated agent can reach it. The moment the thing that authors claims can also sign them, the signature stops meaning anything.

The regulatory perimeter, which is simpler than people fear and trickier than they assume

So long as it's your money and your eyes only, the advice perimeter doesn't bite. You cannot advise yourself, so the Advisers Act, FCA Article 53, the financial promotions regime, MiFID II advice and MAR Art.20 recommendation-disclosure are all inapplicable. That has a design consequence I'd make the most of: the AI can be as opinionated and directive as you want it to be. This plan assumes it should be. Hedged, lawyered output is worse than useless on a desk.

But the trigger is a second person's money or eyes — not a second install. A family member's account, an informal partnership, a fund seeded later, or simply forwarding the AI's output to a friend each cross that line while the software remains a single seat. An earlier draft of this document got that wrong, which is exactly the sort of error that feels safe until it isn't.

Two exposures the single-user framing does not clear

  • Data protection on third parties. The insider archive and person graph are, in plain terms, a profiling database of named natural persons — directors, officers, PDMRs — held for years and enriched with behavioural scoring. UK data protection has a personal-household exemption, but it is read narrowly, and a systematic profiling database built for financial gain sits near its edge. Concretely: keep a register of every table holding identified persons, set a retention policy, and don't extend the graph to inferred personal attributes. There's also a sui generis database right question over the archive itself.
  • EU AI Act: out of scope, but only because you're UK-resident. Its transparency duties attach to a provider, and "putting into service" expressly includes supply for one's own use — so an EU-resident building this for himself could be caught at a single user. Revisit if you relocate.

If a second user ever appears, everything changes at once: you become a redistributor, exchange fees multiply per subscriber, vendor agreements and audit clauses attach, the advice perimeter reappears, and you need an EULA, authentication and a support burden. That's why no-distribution is an architectural invariant with a test rather than a line in a README, and why the MAR wrapper ships dormant rather than absent — dormant is a day's work to enable, absent is a quarter.
